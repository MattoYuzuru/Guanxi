# MS1 live run: home on the Mac, executor on Fedora

**Status:** implemented and fixture-validated on one machine (two real processes over a loopback forward emulator); not yet run
against a real llama-server, a real SSH link or a real Claude Code. **Updated:** 2026-10-23 ·
**Decisions:** D-196 (Fedora real runs), D-197 (Claude Code lead), D-198 (target repository), D-199 (journal stays local).

The **home** node (this Mac) holds the lead, the project clone, the relay workspace, the tools and the acceptance gates. The
**executor** node (Fedora) holds the model: every relay model call is rendered, counted and generated by the executor's
llama-server, through signed F2-d messages ([F2-d hand-off](../plans/lanes/F2-d.handoff.md)). The two nodes talk only over
loopback ports that **you** connect with SSH port forwards; Guanxi binds `127.0.0.1` and refuses any other address.
Each node has two listeners: the **owner API** (workspaces, projects, relay starts, connections; yours alone, never forwarded) and a
**federation listener** that serves nothing but the signed node-to-node API. Only the federation port is forwarded.

```text
Mac (home)                                                         Fedora (executor)
  owner API 127.0.0.1:4551 (not forwarded)                           owner API 127.0.0.1:4552 (not forwarded)
  federation 127.0.0.1:4561 <---- ssh -R 4561:127.0.0.1:4561 ------- peer.url http://127.0.0.1:4561  (renewals, results)
  peer.url http://127.0.0.1:4562 --- ssh -L 4562:127.0.0.1:4562 ---> federation 127.0.0.1:4562
                                                                     llama-server 127.0.0.1:8090 (attached, never owned)
```

Everything below is a command line. Nothing here asks for a secret value: keys are files, configuration holds paths.

## 1. Prerequisites

- **Both machines:** this repository at the same commit, `npm ci`, Node 26 (the commands run `.ts` directly).
- **Mac:** Colima running (acceptance gates run in the K4 container sandbox; the tool never starts or resets it), git, the target
  clone `~/Projects/Guanxi-Test-Repo`. The node's data directory and checkout root must live under your home directory (Colima
  shares it, not `/tmp`).
- **Fedora:** llama.cpp `b11496` and the GGUF, started as an operational service:

  ```bash
  llama-server -m /path/Qwen3.8-27B-IQ3_S.gguf --alias qwen3.8-27b --host 127.0.0.1 --port 8090 \
    -c 32768 -np 1 --jinja --no-context-shift --no-webui
  ```

  `--alias` must equal `model` in the configuration (Guanxi normalises both the same way), `--jinja` is required for the chat
  template round trip, `-np 1` keeps the observed window equal to the whole context. Guanxi attaches to it: it never spawns,
  signals or stops it, and the weights stay resident for as long as you keep it running.
- **Ports.** The peer checks the HTTP `Host` header against *its own federation port*, so each side forwards the **same number** it
  listens on. Defaults: owner API 4551 / 4552 (`--port`), federation 4561 / 4562 (`--federation-port`, `--peer-federation-port`).
  The owner API port must never be forwarded.

## 2. Identities and pairing (once per pairing)

```bash
G="node packages/server/scripts/ms1-live/ms1-live.ts"
# Mac
$G init --role home     --dir ~/ms1/home --model qwen3.8-27b
# Fedora
$G init --role executor --dir ~/ms1/exec --model qwen3.8-27b --llama-url http://127.0.0.1:8090
```

`init` writes `node.key` (mode 0600, never printed or copied), `identity.json`, a public `peer-offer.json` and a configuration
template. It never overwrites a key. Both nodes get the same account id (`--account`, default `owner`), trust `owner_device`, no
admin right and exactly the two scopes a relay pin needs (`attempts`, `replicas`); a peer file carrying more is refused at boot and
by `doctor`. Exchange only the **public** offers:

```bash
scp fedora:ms1/exec/peer-offer.json ~/ms1/home/peer.json
scp ~/ms1/home/peer-offer.json fedora:ms1/exec/peer.json
```

Re-pairing means a new directory and a new data directory: a data directory belongs to the one identity it first booted with
(`local_identity_changed`), and a peer's pinned key is immutable (`identity_conflict`).

## 3. Configuration

`ms1-live.json` is strict (an unknown key, a non-loopback URL or a missing section is an error naming the field) and is the only
switch: the node enters this mode when started with `--config FILE` or `GUANXI_MS1_LIVE_CONFIG=FILE`. Without it nothing in
this document runs and the node boots exactly as before.

| Key | Meaning |
| --- | --- |
| `role` | `home` or `executor` |
| `listen.federationPort` | the loopback port of the federation listener: the one to forward |
| `listen.port` | the owner API port (`GUANXI_API_PORT` overrides; never forwarded) |
| `peer.url` | the other node's federation listener as seen from here: `http://127.0.0.1:<its federation port>` (this side of the forward) |
| `node.*`, `peer.identityFile` | paths of `identity.json`, `node.key` and the peer's offer |
| `model` | the one model reference the executor serves (its `--alias`) |
| `link.*` | dispatch timing: holder TTL, safety margin, model age, reservation, and two deadlines: `requestTimeoutMs` (observe, count, offer: minutes) and `messageTimeoutMs` (everything else, 15 s) |
| `home.alwaysOn` | must be `true`: your assertion that the Mac stays awake (R1 refuses remote attempts without it) |
| `home.reserves` | ADR-0020 reserves in tokens of one window; `preflight` checks them against the observed window |
| `home.checkoutRoot` | optional; default `<data dir>/relay-checkouts` |
| `home.lead` | optional: the Claude Code lead (section 7); its binary paths must be absolute |
| `executor.llamaServer.baseUrl` | the attached llama-server, on the executor's loopback |

The first observation of a model on an executor hashes the whole GGUF (minutes for 11 GB); `link.requestTimeoutMs` defaults to
15 minutes for that reason. The executor warms the hash at start (event `warm`); do not start relays before it says `ready`.

## 4. Start order

```bash
# 1. Fedora: llama-server up (/health answers ok), then
$G doctor --config ~/ms1/exec/ms1-live.json
$G start  --config ~/ms1/exec/ms1-live.json --data-dir ~/ms1/exec/data --json     # wait for {"event":"warm","state":"ready"}
# 2. Mac: the forwards, federation ports only (keep it running; -N only forwards)
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:4562:127.0.0.1:4562 -R 127.0.0.1:4561:127.0.0.1:4561 fedora
# 3. Mac: Colima running, then the home, kept awake for the whole run
caffeinate -dimsu $G start --config ~/ms1/home/ms1-live.json --data-dir ~/ms1/home/data --json
# 4. Mac, then Fedora
$G preflight --config ~/ms1/home/ms1-live.json
$G preflight --config ~/ms1/exec/ms1-live.json --completion
```

`doctor` reads files and probes loopback only; it explains what is missing (`fix:` lines). `preflight` (home) sends a signed
handshake, a signed observation and a signed exact count of a fixed probe through the executor and prints model, window, build,
digest, counter source and the observation time; it also checks `home.reserves` against the observed window. `preflight`
(executor) checks the llama-server through the same class the relay uses, the reverse link, and with `--completion` runs **one
real one-token generation** and compares the evaluated prompt tokens with the count: that is the first real-binary check of the
`/props`, `/apply-template`, `/tokenize` and `/completion` field names, still unverified (R2-op residual 1). If it fails with
`truncation_protocol`, set `executor.llamaServer.cachePrompt: false` and report the build.

Exit codes of every command: `0` ok, `1` a check or the run failed (a doctor with an invalid configuration included), `2` usage
or a configuration that cannot be loaded. `--json` makes stdout one JSON document (`start`: one object per line).

## 5. Register the target repository and run

The relay resolves its project through the node's project and workspace bindings (loopback HTTP, as for any project):

```bash
H=http://127.0.0.1:4551
W=$(curl -s $H/api/workspaces -H 'content-type: application/json' -d '{"rootPath":"'$HOME'/Projects/Guanxi-Test-Repo","name":"guanxi-test-repo"}' | jq -r .id)
P=$(curl -s $H/api/projects   -H 'content-type: application/json' -d '{"name":"guanxi-test-repo"}' | jq -r .id)
curl -s -X PATCH $H/api/agent/projects/$P/roots -H 'content-type: application/json' -d '{"workspaceIds":["'$W'"]}'
```

A plan without a lead goes through the public start (`connectionId` is in the `started` event):

```bash
node packages/cli/src/bin.ts relay exec --url $H --request plan.json --key run-1     # plan.json: projectId, connectionId, model,
                                                                                    # consent "full-access", domains, plan, caps
```

Each model call is a child run on the home (`rc-*`) with one `remote-dispatch:` cost row holding the executor's evaluated tokens.
The relay run keeps its own cap accounting; never add the two.

## 6. Stop

1. Cancel what runs: `curl -s -X POST $H/api/relay/starts/<key>/stop -H 'content-type: application/json' -d '{}'` (cancels, unpins
   the executor, releases the checkout). A lead has no HTTP stop; stopping the home interrupts it.
2. Stop the home (`Ctrl-C` / `SIGTERM`): it closes cleanly. **A relay run does not survive its node** (ADR-0020): anything in
   flight ends `interrupted`, its ledger is kept, the lead must re-delegate.
3. Stop the ssh forward, then the executor (`Ctrl-C`), then llama-server (your service manager).

A pin can stay on the executor when it was unreachable at a stop or crash (`maxPinsPerPeer` is 16, then new relays are refused);
reaping is another lane's work. Inspect it with `sqlite3 <exec data>/guanxi.db "SELECT id FROM federation_streams"`.

## 7. The Claude Code lead (D-197)

`home.lead` makes the home wire K5 and LW from the file: the `claude-code` installation, `guanxi_delegate` through the public relay
start with your `limits`, an executor allow-list of exactly one connection and model, and `alwaysOn`. Fields: `bridge` (absolute
path of the ACP bridge), `bridgeVersion` (exact), `claudeExecutable` (your unmodified CLI), `billingAccount`, `model`,
`runDeadlineMs` (above the longest turn), `domains`, and `limits.maxCaps` (all four caps) with `maxDeadlineMs`.

- **Bridge.** K5 does not run `claude`; it runs the ACP bridge, `https://github.com/agentclientprotocol/claude-agent-acp`
  (npm package `@agentclientprotocol/claude-agent-acp`), with no arguments, and gives it `CLAUDE_CODE_EXECUTABLE` pointing at your
  CLI. It is an operator-installed separate process, never a Guanxi dependency. Install it outside the repository with an exact
  version, then confirm both the entry point and the version it reports before writing them into the configuration:

  ```bash
  npm view @agentclientprotocol/claude-agent-acp version bin
  npm install --prefix ~/.guanxi-agents/claude-agent-acp @agentclientprotocol/claude-agent-acp@<exact version>
  printf '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":1,"clientCapabilities":{}}}\n' \
    | ~/.guanxi-agents/claude-agent-acp/node_modules/.bin/<bin>     # read agentInfo.version
  ```

  `bridgeVersion` must equal that `agentInfo.version` (an absent `agentInfo` records the version as unknown, not as a mismatch).
- **CLI.** `~/.local/bin/claude` resolves to `~/.local/share/claude/versions/2.1.287` at the time of writing; K5 resolves the real
  path at each launch.
- **Sign-in.** K5 launches the bridge with a private `HOME`/`CLAUDE_CONFIG_DIR` under `<data dir>/external-agent-config/`, so your
  everyday login is not used. `start` prints the exact sign-in command (event `lead-login`: executable, `auth login`, and the
  environment *paths*); run it once in a terminal. A run refuses with `claude_login_required` until it has been done, and
  `bare_subscription_unavailable` if `claudeBare` is set. On macOS the login keychain may not be separable by these variables.
- **Start the lead** (the project from section 5 must exist): `$G start --config … --lead-prompt-file prompt.txt --project $P`.
  It binds the lead role, starts one lead and prints `lead-started` and `lead-first`; a node that already has a lead does not start
  another. The lead's turns are billed to your Claude account under the vendor's own policy (unknown to K5).

## 8. Where evidence lands

| What | Where |
| --- | --- |
| relay ledger, gates, head | home `<data>/guanxi.db`: `relay_runs.snapshot`, `relay_public_starts` (admission evidence, status) |
| per-call remote usage | home `run_costs` (`remote-dispatch:*`) on the `rc-*` runs; `remote_dispatch_receipts` (terminal reasons) |
| lead, wakes, packet | home `lead_*` tables, `outbox`; the K2 session log for every run |
| the executor's side | executor `<data>/guanxi.db`: `remote_dispatch_holders`, `remote_dispatch_events`, `federation_streams` (pins) |
| what the model saw | llama-server `/completion` requests on Fedora (not logged by Guanxi; the executor refuses a prompt other than the counted one) |

Nothing prints, logs or stores a key; a private workspace's contents are not logged. When the web UI is not built, `start` prints a harmless
`serveStatic: root path … not found` line on stderr.

## 9. What the forward exposes

The forward carries the **federation listener** only. It serves `/api/federation/*` and answers every other path `404`; it checks
the `Host` header; every request must be signed by the pinned peer key (audience, body hash, nonce, 60-second window), so a
process on the other host that can reach the forwarded loopback port gets `401 unauthenticated` and nothing else. The owner API,
which has no signature and acts as you, is on a different port that is never forwarded; keep it that way, and keep both hosts
single-user (anyone who can log in to the executor can connect to its loopback ports, including the forwarded home federation
port). The keys are what authenticate; `peer-offer.json` is public and carries no secret.

## 10. When something is wrong

| You see | It means | Do |
| --- | --- | --- |
| `peer_unreachable` | nothing listens at `peer.url` | start the peer, open the forward |
| `host_denied` / `peer_forbidden` (403) | the forwarded port differs from the peer's listening port, or identities differ | same number on both ends; compare accounts and scopes |
| `peer_rejected_key` (401) | the peer does not know this key or the clocks differ by over a minute | re-copy `peer-offer.json`; check time on both machines |
| `peer_key_mismatch` | the answer was not signed by the key in the peer file | wrong peer file, or the forward points at another node |
| `peer_unavailable` (503) from the home | the executor cannot serve (usually its llama-server) | run the executor's `preflight` |
| `llama_server_unavailable` / `llama_server_identity` | not reachable, or alias or model file not readable here | start with `--alias`, check the URL and file |
| `truncation_protocol` | the server evaluated other tokens than it counted | `cachePrompt: false`, report the build |
| `runtime_observation_stale` on the first start | the model hash was not warm | wait for `warm`, rerun `preflight` |
| a run ends `interrupted` after the Mac slept | leases are timed on a clock that does not count suspend; `home.alwaysOn` only asserts, nothing arranges it | run under `caffeinate -dimsu`, on power |

A relay start that fails for any of these creates no run, no session and no checkout, and never runs a model on the Mac.
