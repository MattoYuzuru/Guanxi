## Outcome

The optional T0 `agent.external` kernel service implements five ACP v1 profiles (Claude Code,
Copilot, Gemini CLI, OpenCode, Goose), Codex app-server and official-CLI Sign in with ChatGPT.
It is activated by trusted `StartOptions.externalAgents`, not program discovery or an HTTP
executable-path endpoint. Current operation/setup and limitations are in the
[module guide](../../../packages/server/src/external-agents/README.md).

- K3 dispatch enforces the **original prompt author's** ownership before subscription launch,
  even with a sharing grant. API editor payment requires an owner-only persisted grant. No
  prompt/body supplies an authenticated identity. Delegating callers must preserve the author.
- Manual roles bind connection/backend/model/params: explicit session override, then project
  default; null/invalid overrides refuse without a spend fallback. Native bindings resolve for
  K4; external `run` does not turn a native connection into an external one.
- Only the owner's separately installed Claude ACP bridge and unmodified `claude` are used.
  The bridge depends on proprietary Agent SDK code **outside Guanxi**. No Claude binary/SDK
  is installed, bundled, copied or declared as a dependency here.
- Exact-pinned `@agentclientprotocol/sdk` **0.29.0**, Apache-2.0, supplies wire types/constants.
  Its installed license and upstream license were checked. Its client parser is deliberately
  unused: independent review demonstrated raw-frame logging and default-success RPC handlers.
  A shared quiet RPC transport refuses fs/terminal/token requests and discards thoughts.
- Subscription HOME/config paths are isolated by node/owner/connection; each node signs in
  locally with its unmodified CLI. API agents get fresh directories per invocation and remove
  them after the child closes. OpenCode forces the K3 provider/model and an API-key environment
  reference and denies all tools; Goose forces provider/model in chat mode and disables keyring
  fallback. Both refuse a non-owner actor with `host_tools_owner_only`. One subscription owner
  per adapter/node is enforced with `adapter_owner_conflict`. External-local execution refuses
  until exact host/context and governor integration exists; K4's native path continues to own
  local inference.
- Requests, response text and K2 events use the real scrubber. Split response secrets are
  reassembled before final scrubbing. No raw stderr, protocol errors, thought content, auth
  URL or vendor credentials are written to Guanxi logs. Codex plans are correlated by thread
  and turn; ACP plans report completed work as verification requested.
- Codex quota reads/notifications and the Claude statusline ingestion boundary retain dated
  provenance. Account reports use the maximum for an equivalent reset window, never a sum;
  ISO spellings normalize to the same instant. Account grouping is operator metadata. The
  learning sidecar records successful concurrency and explicitly classified rejections; local
  admission applies the operator policy and learned rejection ceiling. There is no distributed
  lease or estimate that silently becomes a vendor limit.

This is a headless kernel slice. No web/UI, public REST/SSE schema, federation or runs code was
changed. No UI primitives, review records or suppression files were changed. R3 automatic
routing, external relay execution and F1 report transport are not implemented by this lane.

### What was not possible, and residual risk

- Codex app-server exposes no documented deny-all host-tool field in this slice. Threads now ask
  (`approvalPolicy: on-request`) instead of `never`, and this client refuses every approval RPC;
  the read-only sandbox still permits reads, so Codex host access is not fully denied.
- Claude Code, Copilot and Gemini CLI expose no adapter-level deny/ask setting in this code.
  They are left unchanged and no containment is claimed. Gemini CLI is API-key paid but is not
  in the `host_tools_owner_only` set, per the instruction to keep the non-owner refusal to
  OpenCode and Goose in this pass.
- The static check is text-level. It cannot prove the absence of a path computed entirely at
  runtime with no vendor-path text in the module (`join(home, pieces[0], pieces[1])`), a vendor
  CLI's internal file access, or dynamic code outside the scanned tree. On this tree
  `checkVendorCredentials()` reported no hits inside or outside K5, so no allowlist or
  out-of-K5 edit was needed.
- L2 asserts the protocol-first cancel frame and bounded settlement; it does not measure the
  exact 2 s/3 s SIGTERM/SIGKILL instants, which would race OS signal delivery.
- M3 is enforced when the external-agent policy is configured (the installation list), not when
  a K3 connection row is created; a second owner's connection is refused before any run.
- M4 records the connection-wide, non-expiring grant default; the code is unchanged and the
  question is open (Q-245).
- Per instruction, full `npm test`, builds, browser gates and a real vendor CLI were not run;
  the integrator owns the full gates. No real HOME, keychain, vendor CLI or network was used.

## Storage, rollback and residual risk

K5 adds only the private `external-agents.sqlite` sidecar (append-only `k5_migrations` v1).
No existing SQLite migration or public wire field changes. Remove/disable the optional plugin
to roll back, retaining the sidecar and vendor configuration; do not delete logins or vendor
state. Existing native execution and connection APIs remain unchanged.

External agents are trusted installed programs with internal tools, **not K4 ExecutionOwner
sandboxes**. Private cwd and denied client RPCs do not contain their own host access or model
calls. Guanxi scrubs process-boundary input/output; it cannot intercept a vendor's internal
tool/model traffic. Ordinary process-group children are cleaned; escaped/detached descendants
are outside this boundary. No untrusted arbitrary executable is accepted from HTTP.

Operational billing, effective implicit bare defaults, real release compatibility, automatic
Claude quota production and distributed account admission remain unverified/unfinished as
specified above. Account grouping and cross-node quota ingress require trusted identity
mapping/authentication from the later consumer. Known API keys are supplied only to the
configured process environment. No subscription tokens are inspected, relocated or exported.
